# DayZ UI scripting realities (Tier 2 topic)

Part of Tier 2. Where DayZ UI colors come from and how each source is overridden. Read it together with the core rules in `skills/_shared/dayz-conventions.md`, which still apply.

## UI scripting realities (read before any "change the X color" task)

DayZ's UI has no central theme system; no `PrimaryAccentColor` constant flows through every widget. A color comes from three independent places, each overridden differently:

1. `.layout` files in `P:\gui\layouts\` (100+ files). Colors are baked per widget as RGBA values. `modded class` does not apply to a `.layout` itself. A layout is loaded by script through its virtual path, for example `P:\scripts\5_mission\gui\newui\mainmenu\mainmenu.c:59` calls `CreateWidgets("gui/layouts/new_ui/main_menu.layout")` and `P:\scripts\5_mission\mission\missiongameplay.c:132` calls `CreateWidgets("gui/layouts/day_z_hud.layout")`. A copy placed in your mod's own `gui/layouts/` sits under your PBO prefix (`MyMod/gui/layouts/...`) and replaces nothing. Pick one of two routes:
   - **Recolor a few widgets (cheapest, survives updates best):** `modded class` the loading class, override the loading method, call `super` first so vanilla loads and wires the layout, then look the widget up on the loaded root and recolor it. The HUD root is the field `m_HudRootWidget` (`missiongameplay.c:8`), and `missiongameplay.c:140` looks up the widget `"HudPanel"` on it, so `modded class MissionGameplay { override void OnInit() { super.OnInit(); if (!m_HudRootWidget) return; Widget w = m_HudRootWidget.FindAnyWidget("HudPanel"); if (w) w.SetColor(0xFF2060FF); } }` (`Widget.SetColor(int color)` is declared at `P:\scripts\1_core\proto\enwidgets.c:144`) recolors that panel without touching the layout file. Unverified (not tested in game): whether `SetColor` on a container panel visibly tints its children depends on the widget types in `day_z_hud.layout`; target the exact child widget you see in the layout when it does not.
   - **Replace the whole layout:** override the method that calls `CreateWidgets` and point it at your copy (`"MyMod/gui/layouts/new_ui/main_menu.layout"`). Because the call and the child-widget wiring sit in the same method (`mainmenu.c:61` onward runs `FindAnyWidget` on the new root), you reproduce that method's body instead of calling `super`, and keep every widget name the script looks up. This works only for a method that does not itself call `super`, such as `MainMenu.Init` (`mainmenu.c:57`). For the HUD it works but costs more than it gives. The `CreateWidgets` call sits inside `MissionGameplay.OnInit` (`missiongameplay.c:102` onward), whose first line is `super.OnInit()` (`missiongameplay.c:104`). Neither `MissionBase` (`P:\scripts\5_mission\mission\missionbase.c`) nor `MissionBaseWorld` (`P:\scripts\4_world\classes\missionbaseworld.c`) defines `OnInit`; the only parent body is the empty `void OnInit() {}` in class `Mission` (`P:\scripts\3_game\gameplay.c:700`). So a `modded class MissionGameplay` override that reproduces the body, leaves out that first `super.OnInit()` line (inside a modded override `super` would run the vanilla body, layout load included) and points `CreateWidgets` at your copy loses no vanilla parent init. The cost is elsewhere: skipping `super` also skips every other mod's modded `MissionGameplay.OnInit` loaded before yours, and your copy of the body goes stale whenever a DayZ update changes vanilla `OnInit`. Setting `m_HudRootWidget` yourself before calling `super` is no shortcut, because the `if ( !m_HudRootWidget )` guard (`missiongameplay.c:130`) then skips the `Chat`, `ActionMenu` and `Hud` `Init` calls. Prefer the recolor route for the HUD for those two reasons. Whole-layout replacement of any layout is brittle across DayZ updates.
   
   Unverified (not tested in game): shipping a PBO whose prefix is `gui` so the file lands at the same virtual path `gui/layouts/...` is reported to shadow the vanilla file, but it collides with the vanilla prefix and depends on load order; test it before relying on it.
2. Inline ARGB literals in `P:\scripts\5_mission\gui\` (10+ files), such as `w.SetColor(0xFFFFEC44)` in `actionmenu.c:74`. Override the containing class's method with `modded class`, not the constant.
3. `Colors` / `FadeColors` constants in `P:\scripts\3_game\colors.c`. The values are `const int` members (`P:\scripts\3_game\colors.c:53` declares `const int COLOR_DAYZ_RED = 0xffd70d11;`). Unverified (reported, not tested in Workbench): `modded class Colors { const int X = ...; }` is said to be a no-op because callers bake the original constant value at compile time. Test it in Workbench before relying on it either way. `COLOR_DAYZ_RED` is referenced in one place across vanilla scripts (`P:\scripts\5_mission\gui\newui\mainmenu\mainmenupromo.c:157`), so even a working override would only recolor the main-menu promo banner.

So "change all the red UI to blue" is not a one-file task: it means sweeping `.layout` files per widget and overriding every class method that calls `SetColor(<red ARGB>)` in `5_mission/gui/`. That is hours of work. For one-off recolors, scope the task to one element. For a new mod that needs theming, a third-party UI framework may supply the theme layer the engine lacks. Unverified (this repo has not checked any such framework's source or API): CUI (Community UI Framework) is reported to offer one; read its own source and confirm the API exists before you build on it or recommend it.

When the user asks for a color or theme change, ask for scope first (single element or sweep) and warn about the layout/script split before invoking any agent.
