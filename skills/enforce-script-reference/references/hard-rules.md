# Enforce Script hard rules

The rules to apply to every piece of Enforce Script, each one tied to a crash, a failed compile or a silent failure seen in a real mod. Rule numbers are the ones the other reference files cite ("rule 24", "rule 37b"); the numbering repeats 12, 13 and 34, so those references name the section too.

How to read the evidence: a line cited as `P:\...:N` was opened on `P:\` and holds what the text says. "Measured in game" names the mod and game build that measured it; those results were not re-run for this pack. Line numbers given for 1.29 are for a build that is not on `P:\`. `[EXACT]` marks a fact read in the cited file, `[DESIGN]` a recommendation. `SP-`, `LL-` and `CLAIM-` labels are the knowledge pack's own entry names, kept because its other files use them.

## Check the symbol is real before you call it

Before treating any vanilla Enforce API as callable, check that it is not inside an `#ifdef` whose macro is never defined in the tree. Search `P:\scripts\` for `#ifdef <MACRO>` and `#define <MACRO>`: if only `#ifdef` hits appear, the code is dead in this build and the symbol does not exist.

The standard case: `ActionManagerClient.PerformAction(int user_action_id, ActionTarget, ItemBase, Param)` at `P:\scripts\4_world\classes\useractionscomponent\actionmanagerclient.c:798` is a correct citation, but it sits inside `#ifdef BOT` (opens `:796`, closes `:802`). `BOT` appears in the whole vanilla tree only as `#ifdef`, never as `#define`, so the symbol does not exist in retail or diag. The real public entry point for starting an action from script is `PerformActionStart(ActionBase, ActionTarget, ItemBase, Param)` at `:804`, outside the block. Until 1.29 the `#ifdef BOT` block was `ActionManagerClient.c:754-760`, `PerformAction` was `:756` and `PerformActionStart` was `:762`. Since 1.30, in single player `PerformActionStart` ignores a second call while an action is pending or current, and `GetActionState()` can return `UA_AM_INIT` while one is pending. The bodies are in `dayz-1-30-enforce-script.md`.

The same check applies to `proto native` declarations: a correct citation does not prove the function is linked. `GetFPS` is declared `proto native int GetFPS();` at `P:\scripts\1_core\proto\proto.c:147` (the same line in 1.29), yet in DayZDiag 1.29 every call throws `Virtual Machine Exception — Function 'GetFPS' not linked` (measured in game 2026-09-14, not re-run here). A `proto native` line proves the declaration exists, not that the engine registered a native behind it: call a `proto native` API once from a throwaway script before building logic on it.

`CCINone` does not mean "hands must be empty". `CCINone.Can()` returns `true` for anything (`P:\scripts\4_world\classes\useractionscomponent\itemconditioncomponents\ccinone.c:3`). It means "no item condition". Reading it as "hands empty" produces dead checks and a hunt for a fault that does not exist.

## Persistent time and player identity (SP-207)

Before persisting or ordering data across restarts, check both the clock and the identity source:

- `GetTime()` on `CGame` is mission time in milliseconds (`P:\scripts\3_game\global\game.c:1534`). It restarts on every boot. Use it for durations inside one session, never for a durable timestamp or for ordering across restarts.
- Build wall clock timestamps from `GetYearMonthDayUTC` (`P:\scripts\1_core\proto\ensystem.c:100`) and `GetHourMinuteSecondUTC` (`P:\scripts\1_core\proto\ensystem.c:76`). Store every UTC part the ordering needs.
- `PlayerIdentity.GetId()` is the hashed identity meant for databases and logs (`P:\scripts\3_game\gameplay.c:367-368`). `GetPlainId()` is marked as not for databases or logs (`:369-370`), and `GetPlayerId()` is a session ID that is reused after the player disconnects (`:371-372`). Neither of those two is a durable ownership key.

## Syntax rules

1. **No ternary operator.** `condition ? a : b` does not compile.
2. **`++` and `--` work**, prefix and postfix: `++i`, `i++`, `--i` (seen in LBmaster's production mods; vanilla uses them everywhere).
3. **`foreach` works**: `foreach (Type var : array)` and `foreach (key, value : map)`. Do not run `foreach` over an expression that returns a temporary collection (reported to hit a null pointer; see `memory-management.md`).
4. **`+=` and `-=` work.** `x += y;` is the same as `x = x + y;`.
5. **String literals as function arguments work.** `MyFunc("hello", "world")` is fine.
6. **Multi-line expressions are only partly safe.** Compiles have broken on a boolean condition split across lines at `&&` or `||` (the LF_VStorage and HUD_Mod projects) and on a string `+` chain continued on the next line (a bone dump `Print` in the `dayz-animation-pipeline` material). Keep conditions and string builds on one line, or split them into single-line statements (`ln = ln + ...;`). This is the legacy rule ENF-R11g (see the map at the end). A call whose argument list spans several lines killed the whole file and its module in game (`Can't compile "Mission" script module!`, the server did not start; DayZDiag 1.29.163451, SP-127). The error is reported on the line of the next argument, not the opening line, and the errors that follow (`Syntax error` on line 1, `Unexpected scope` on line 2) look like a corrupt file. Vanilla does contain some multi-line argument lists (`Math.Lerp(` at `P:\scripts\3_game\worlddata.c:153-156`, `new NotificationData(` at `P:\scripts\3_game\client\notifications\notificationsystem.c:307-311`), so exactly what is safe is not known. Offline check: any line that ends in `(` or `,` after comments and trailing spaces are stripped is a risk; the test `test_probe_mission_keeps_every_call_argument_list_on_one_line` in `scripts\tools\dayz-ui-lab\tests\test_probe.py` found 7 such lines in the failing file and 0 in the fixed one. A mod that fails to compile still passes any test that only reads the source text: the three tests covering that file were green while the engine rejected it.
7. **Do not reuse a variable name in sibling `if` and `else` blocks.** Declare it once before the condition (see "method scope" in `compiler-traps.md`).
8. **No `new array`, `map` or `Param` inside periodic ticks.** Use `m_` fields and `Clear()` them each tick.
9. **Type everything explicitly; prefix every member field with `m_`.**
10. **Declare variables before loops and conditions.**
11. **Inline string concatenation works.** `"Count: " + val + " items"` is valid.
12. **A class constant read from a `static` method must be `static const` (LL-478).** A plain `const` there was fatal on a retail server (measured in game by the knowledge pack's author). The compile check is a retail boot with `SERVER` defined, done before any review; when errors cascade, fix the first one only and compile again.
13. **`%` works only with integers.** `float ox = (n % 4) * 0.7 - 1.05;` with `int n` fails with `Unknown operator '%'` and kills the mission init compile (measured in game on DayZ 1.30.164014 Exp, and again on DayZDiag 1.30.164289 in a mod's `4_World`; see `pitfalls-advanced.md`). [EXACT][CLAIM-ENF-MODULO-INT-ONLY] Every vanilla modulo has integer operands, for example `new_index % count` (`P:\scripts\1_core\proto\enscript.c:652-661`) and `startTime.ToInt() % 100` (`P:\scripts\3_game\cfgbunkerbroadcastjsondata.c:196`). Compute the modulo into an `int` first (`int col = n % 4;`) and multiply the float afterwards.

### More things the language lacks (from the StarDZ modding wiki)

Traps reported by the StarDZ DayZ modding wiki that the rules above do not cover. A row with a `P:\` citation was checked there; the others are that wiki's reports, not yet checked on `P:\`.

| Trap | What to do | Evidence or label |
|---|---|---|
| No `do ... while` | Use `while` or `for` | No vanilla script under `P:\scripts\` uses `do`. CLAIM-STARDZ-ENFORCE-SYNTAX-ABSENCES |
| No `try`, `catch` or `throw` | Return a failure value; do not invent exception flow | Same label; also `skills/_shared/enscript/patterns/language_workarounds.md` |
| `switch` cases fall through without `break` | Always `break` unless you mean to fall through | Same label |
| No `nullptr` | Use `null` or `NULL` | Same label |
| No `#include`, no namespaces | Script modules come from `CfgMods` `defs` in `config.cpp` | Same label |
| Default parameter values must be literals or `NULL` | No call expressions as defaults | Same label |
| `GetGame().GetPlayer()` is `null` on a dedicated server | It is the local player only; on the server use `GetPlayers` (`P:\scripts\3_game\global\game.c:945`). This is a different `null` from the one during client preload (`runtime-traps.md`) | CLAIM-STARDZ-GETPLAYER-SERVER-NULL |
| `sealed` types and methods (1.28 and later) | They cannot be extended or overridden | Vanilla declares `sealed class Contact` (`P:\scripts\1_core\physics\contact.c:9`) |
| A method takes at most 16 parameters (1.28 and later) | Pass a data class instead | StarDZ gotcha 32 |
| `array.Remove` does not keep order | It moves the last element into the gap (`P:\scripts\1_core\proto\enscript.c:457-463`); use `RemoveOrdered` (`:470`) when order matters | StarDZ gotcha 23 |

More one-line reports from the same wiki: string methods may change the string in place; an empty `#ifdef` or `#ifndef` block can crash the compile (not reproduced: a block holding only a comment compiled and ran on DayZDiag 1.30.164289, `pitfalls-advanced.md` section 5); a `crash_*.log` file name does not prove an engine crash; compile errors sometimes name the wrong file; put parentheses around a bitwise test before comparing it; `Obsolete` warnings (1.28 and later) deserve cleanup. The wiki also says `JsonFileLoader.JsonLoadFile` returns `void`; see SP-136 in `networking.md` for what to call instead.

## Memory rules

12. **`ref` on a class member field keeps its target alive.** On a local it is valid and redundant (locals are strong by default). Never put it on a function parameter or a return type: the DayZDiag compiler makes `ref` on a method parameter a fatal compile error while the retail compiler lets it pass (SP-047 row in `review-and-troubleshooting.md`).
13. **Never combine `ref` and `autoptr`** on the same field. Pick one.
14. **Do not use `delete` in mod code.** The knowledge pack's rule is that a `delete` on an object something else still uses ends in a segfault, and that setting the reference to `null` is enough. `delete` itself is legal and vanilla uses it on script objects it owns (`delete GetBleedingManagerServer();`, `P:\scripts\4_world\entities\manbase\playerbase.c:1224`); it is never the way to remove an entity. `skills/_shared/enscript/references/language_memory.md` has the full rules.
15. **A class field without `ref` is weak, for `Managed` and plain classes alike**, and reads `NULL` once the last strong reference goes. Locals are strong by default, and `ref` keeps a plain class alive too (measured on one probe; see `memory-management.md`).
16. **Break reference cycles in destructors.** Reference counting cannot free a cycle.

## Networking rules

17. **Write synced variables only on the server**, inside `#ifdef SERVER`, and call `SetSynchDirty()`. (Code that must also run in single player uses `GetGame().IsServer()` instead, because `SERVER` is not defined there; see `skills/_shared/enscript/references/language_compile.md`.)
18. **Check the return value of every `ctx.Read()`** and return on failure.
19. **`GetGame().IsServer()` returns true on the client during load** (reported by the knowledge pack). Use `IsDedicatedServer()`, which vanilla documents as the "robust check ... valid much sooner" (`P:\scripts\3_game\global\game.c:1121-1125`).
20. **`GetGame().IsClient()` is not reliable on the client during load** (inferred from rule 19; do not assume an exact value). Use `!IsDedicatedServer()`.
    - Rules 19 and 20 are about load and init time: constructors, module init, `OnInit`. In callbacks after load (`OnRPC`, `EOnContact`, per tick), `GetGame().IsServer()` and `IsClient()` are safe and are what vanilla uses.
    - Until 1.29 the inventory network path was `DayZPlayerInventory.ProcessInputData`. Since 1.30 retail does not call `ProcessInputData`: that call site is inside `#ifdef DIAG_DEVELOPER` and also needs `PluginInventoryDebug.IsOldProcessInputDataEnable()`. The live path is `ValidateInventoryCommandServer`, `ExecuteInventoryCommandServer`, `ExecuteInventoryCommandClient` and `ExecuteInventoryCommandRemote`, plus `INPUT_UDT_INVENTORY_CHECK` and `OnInventoryCheck`. See `dayz-1-30-enforce-script.md`.

## Timer rules

21. **`CallLater` is reported to lose precision after about 4.5 hours** (blamed on a 32 bit float). This cannot be checked on `P:\`: `CallLater` is `proto` and takes its delay as an `int` of milliseconds (`P:\scripts\2_gamelib\tools.c:61`). Treat it as a report; `skills/_shared/enscript/patterns/scheduler.md` gives the `Timer` alternative.
22. **One repeating `CallLater` per device fragments the heap** and crashes after hours (reported from the LFPowerGrid mod).
23. **Run all periodic ticks from one manager** with a register and unregister pattern.
    - A singleton manager is not enough on its own. Its `Reset()` on reconnect orphans the repeat timer, because the `Remove()` lives in the destructor of the instance being dropped: the queue keeps firing into the dead object (duplicate ticks, then a crash). Drive those ticks from the mission's `OnUpdate` with a `timeslice` accumulator and fetch the singleton through `Get()` each frame: nothing is registered, so nothing can be orphaned. Reset the accumulator to zero when it fires (do not subtract the period) so a long hitch fires once, not in a burst. Do not skip the maintenance call when "there is nothing to draw": retry and reconcile ticks exist to build what is not drawn yet. Measured in LFPowerGrid on 2026-09-08: five repeating `CALL_CATEGORY_GUI` chains became one `MaintenanceTick(timeslice)` per renderer.

## Override rules

24. **An `override` uses the same parameter names as the base class.** The knowledge pack reports that mismatched names cause a silent runtime failure.
25. **A `modded class` can add member variables.** LBmaster's modded `DayZGame` adds more than ten in production. Confirmed for `DayZGame`, probable for other classes; for `ItemBase` and `PlayerBase` a static map keyed by entity ID is the cautious choice if you are unsure. (`skills/_shared/enscript/patterns/modded_class.md`, "Adding fields safely", shows the direct form.)
26. **Two `modded class` declarations of the same class can coexist** in different files.
42. **A recipe's `CanDo` copies `ingredients[0]` and `[1]` to locals first and does not call `super.CanDo`.** [EXACT][CLAIM-ENF-RECIPE-CANDO-SUPER] Measured in game (DayZDiag 1.29, 2026-09-27, one world craft recipe): a `CanDo` override that began with `if (!super.CanDo(ingredients, player)) return false;` and then cast `ingredients[1]` and `[0]` returned false on the server while every part of its condition read true, so `ActionWorldCraft.ActionConditionContinue` (server side, `P:\scripts\4_world\classes\useractionscomponent\actions\continuous\actionworldcraft.c:89-107`) cancelled the craft as it started. A probe that wrapped that override and read the array after its own `super` call found the same item in both slots: the tray twice, where the sorted pair was leaves and tray. Copying both slots to locals and dropping the `super` call fixed it in game; the same commit also split the final `return tray && ...` into a null guard, so which change mattered was not isolated. Vanilla almost never makes that call: of 206 `CanDo` overrides in `4_world/classes/recipes/recipes/`, only `P:\scripts\4_world\classes\recipes\recipes\craftlongtorch.c:61` does, as its only statement (`return super.CanDo(ingredients, player);`). Without `super` the recipe loses the one check in `RecipeBase.CanDo`, no ingredient with attachments (`P:\scripts\4_world\classes\recipes\recipebase.c:551-561`); a recipe that needs it can repeat it on the locals (not tested). Not established: the mechanism, which of the commit's changes was needed, whether a `super` call made after the copy is harmless, and whether vanilla's `return super.CanDo(...)` form is affected.

## Serialization rules

27. **`[NonSerialized()]` keeps a field out of serialization.** Use it on runtime only fields (`P:\scripts\1_core\proto\serializer.c:16`). Test that the field stays out of your JSON before you rely on it.
28. **Remove `ScriptInvoker` subscriptions in the destructor**, and null check the invoker first: `if (MyClass.Event_X) MyClass.Event_X.Remove(callback);`
29. **`Widget.Unlink()` destroys the widget and all its children** (`P:\scripts\1_core\proto\enwidgets.c:173`). Use it for UI cleanup instead of `delete`.

## Action rules

30. **Use `CCINonRuined` for an action that needs an item in hand.** `CCINone` means "no item condition" (see the top of this file), so it does not check the tool; the knowledge pack also reports that with `CCINone` plus a tool check in `ActionCondition` the action may not appear while the tool is held. `skills/_shared/enscript/patterns/actions.md` has the condition table.
31. **Check tools with `IsKindOf()`, not `GetType() ==`.** An exact `GetType()` match fails on inherited and modded variants; `IsKindOf()` walks the inheritance chain.
32. **Make the client and server tool checks the same.** If `ActionCondition` uses `IsKindOf`, the server RPC handler must use `IsKindOf` too, not `GetType() !=`.
33. **`RemoveAction(ActionTakeItem)` and `RemoveAction(ActionTakeItemToHands)`** stop a placed object from being picked up or dragged; combine them with `IsTakeable()` and `CanPutInCargo()` returning false.
34. **Test which selection the cursor component belongs to through the engine's name list, in lower case.** `GetActionComponentNameList(idx, list, "")` (`P:\scripts\3_game\entities\object.c:192`) returned `component14`, `component19` and `door1` for a runtime `House` (the LFSecure mod's room, in game 2026-09-09): the names are lower case, and the cursor index is 0 based while Object Builder's automatic names are 1 based (`comp 13 → component14`, `comp 18 → component19`, `comp 8 → door1`). `IsActionComponentPartOfSelection(idx, "Component14", LOD.NAME_VIEW)` never matched, so three actions (bed, sink, exit) were dead for a whole test cycle with no error anywhere. Compare `list.Get(i)` after `ToLower()` with lower case names in the default geometry, and while diagnosing log `idx` and the name list once per distinct index.
40. **A liquid container derived from `Bottle_Base` inherits the whole vanilla liquid action set; decide every one.** [EXACT][CLAIM-ENF-BOTTLE-LIQUID-ACTIONS] `SetActions` adds 14 liquid actions in 1.29 (1.29 `bottle_base.c:354-372`) and 16 in 1.30 (`P:\scripts\4_world\entities\itembase\edible_base\bottle_base.c:356-376`); each is a way in or out. The fill action takes gasoline from a pump: `m_AllowedLiquidMask = LIQUID_GROUP_DRINKWATER | LIQUID_GASOLINE` (`P:\scripts\4_world\classes\useractionscomponent\actions\continuous\actionfillbottlebase.c:41-44`; in 1.30 the action `Bottle_Base` adds is `ActionObtainLiquidBase`, which sets the same mask at `P:\scripts\4_world\classes\useractionscomponent\actions\continuous\actionobtainliquidbase.c:50`). With your container as the target, drain and pour belong to the held item: their `ActionCondition` is in `P:\scripts\4_world\classes\useractionscomponent\actions\continuous\actiondrainliquid.c:33-42` and `P:\scripts\4_world\classes\useractionscomponent\actions\continuous\actionpourliquid.c:33-42`. Removing them in the container's own `SetActions` hides nothing: close them with a `modded` action's `ActionCondition` on `target.GetObject()`, or gate the liquid itself by overriding `GetLiquidContainerMask()`, the only input of `Liquid.CanFillContainer` (`P:\scripts\4_world\static\liquid.c:248`). The vanilla continuous pour can stop short of full (960 of 1000 ml measured once in a local DayZDiag game): a rule that demands exact fullness needs a tolerance, or must complete in `OnEndServer` (`P:\scripts\4_world\classes\useractionscomponent\actionbase.c:1409`).
41. **`ActionEmptyBottleBase` overrides `OnStartAnimationLoop` and `OnEndAnimationLoop` without `super`** (`P:\scripts\4_world\classes\useractionscomponent\actions\continuous\actionemptybottlebase.c:70-78`). [EXACT][CLAIM-ENF-EMPTYBOTTLE-LOOP-OVERRIDE] In its subclasses the protected `OnStartAnimationLoopServer`, `OnStartAnimationLoopClient` and `OnEndAnimationLoop*` variants of `ActionContinuousBase` (`P:\scripts\4_world\classes\useractionscomponent\actions\actioncontinuousbase.c:272-286`, they set `m_WasActionStarted`) never run, with no error. Hook the public loop callbacks instead (called on both sides, `P:\scripts\4_world\classes\useractionscomponent\actions\actioncontinuousbase.c:197-242`) and act only on the server; `OnEndServer` (`P:\scripts\4_world\classes\useractionscomponent\actionbase.c:1409`) also runs after an interrupt and is the safe place to reset.

## Layout and UI path rules

34. **Layout paths must match `$PBOPREFIX$`.** If the prefix is `SimpleGroup`, paths must be `SimpleGroup/gui/layouts/...`, not `LFPG_Territory/gui/...`. A mismatch crashes and leaves a ghost menu in `UIManager` (reported from the LFPG mods).
35. **Guard the construction of a Dabs `ScriptViewMenu`.** Check `GetLayoutRoot()` after `new`; if it is null, set the singleton to null (do not `delete`). A failed `ScriptViewMenu` leaves a ghost entry in `UIManager` that blocks every later menu.

The full UI, layout and Dabs material is in the `dayz-ui-development` skill and in `skills/_shared/enscript/integrations/dabs_framework.md`.

## Input and keybind rules

36. **The root tag of `inputs.xml` is `<modded_inputs>`**, not `<modinfo>` (a common mistake). `<actions>` declares the input names and `<preset>` assigns default keys.
37. **`config.cpp` must point at the inputs file** with an `inputs` entry in `CfgMods`. The knowledge pack writes it with backslashes (`inputs = "ModName\\inputs.xml";`); shipped mods also use forward slashes from the PBO prefix (`inputs = "MyMod/data/inputs.xml";`, see `skills/_shared/enscript/integrations/input_bindings.md`).
37b. **An `<exclude>` that includes `inventory` silently kills mouse look.** `inventory` includes `aiming` (`P:\bin\specific.xml:242` to `:244`), and `aiming` is exactly `UAAimLeft`, `UAAimRight`, `UAAimUp` and `UAAimDown` (`:149-154`). Any custom camera, sight or scripted view that suppresses `inventory` while active reads 0.0 from every look axis, with no error anywhere. The symptom that identifies it: the camera answers WASD (raw `KeyState` bypasses excludes) but ignores the mouse. Fix: expand to inventory's own contents minus `aiming` (`gestures`, `stances`, `optics`, `actions`, `UAUIGesturesOpen`), and read the axes the way the vanilla spectator does: `GetUApi().GetInputByID(UAAimLeft).LocalValue()` (`P:\scripts\4_world\entities\dayzspectator.c:39-44`). Measured 2026-08-19 (LFHeli mod, FLIR sight): the two halves are independent, so fixing one alone changes nothing. There is a third lock that is easy to re-arm on purpose: `menu` also includes `inventory` (`P:\bin\specific.xml:277` to `:278`), so keeping `menu` in the exclude set "as a safe fallback" restores the exact suppression you just removed from your own group. In the same session the private group was cleaned of `inventory` and the mouse stayed dead for another two build cycles because `menu` was still in the array. If a sight needs the look axes, nothing in the exclude set may reach `aiming` through an include: expand every group you pass and check, do not trust its name.
37c. **Taking the camera from a seated player destroys the `HumanCommandVehicle`.** The `SelectPlayer(null)` plus `SelectSpectator(...)` pattern (from Community Online Tools and CCTV mods) was written for a player on foot. From a vehicle seat, `SelectPlayer(identity, player)` on exit restores the pawn but not the vehicle command: the player is left frozen while every cleanup log line reports success. Rebuild it as vanilla does after unconsciousness: `StartCommand_Vehicle(transport, CrewMemberIndex(p), GetSeatAnimationType(idx), true)` (`P:\scripts\4_world\entities\dayzplayerimplement.c:2391-2396`; the proto is at `P:\scripts\3_game\human.c:1526`). Pair it with `ResetGameFocus()` beside the `ChangeGameFocus(-1)` (`P:\scripts\5_mission\gui\cameratools\cameratoolsmenu.c:797-800`): `HasGameFocus` is true only at exactly 0 (`P:\scripts\3_game\tools\input.c:29-34`). In a vehicle, vanilla picks the camera from `m_Camera3rdPerson` whenever the server allows third person (`P:\scripts\4_world\entities\dayzplayerimplement.c:2891-2914`; 1.29 `:2849-2868`), so a sight must force first person with `SetIsInThirdPerson(false)` (`:307-310`) and restore the previous value on exit, or entering in third person leaves the operator outside the aircraft. Measured outcome on 2026-08-19: the rebuild is necessary but not sufficient. With the vehicle command rebuilt, the probe read `vehCmd=true seat1=true parent=true inVeh=true` and the operator was back in the seat, yet the camera never came back: the view stayed where the sight was, no action was offered, and the mouse moved only the head, as if free look had stuck on. Taking the pawn back does not re-create the player camera. Do not spend time hardening this path; use 37d.
37d. **A sight or turret on a seated player should never give up the pawn at all.** Instead of `SelectPlayer(null)` plus `SelectSpectator`, mod vanilla's own vehicle camera and write its transform. `CameraHandler` returns `DayZPlayerCameras.DAYZCAMERA_1ST_VEHICLE` (= 30, `P:\scripts\4_world\entities\manbase\dayzplayer\dayzplayercameras.c:18`, registered at `:61`) while the sight is up, and `modded class DayZPlayerCamera1stPersonVehicle` (`P:\scripts\4_world\entities\manbase\dayzplayer\dayzplayercameravehicles.c:4`) overrides `OnUpdate` to fill `pOutResult.m_CameraTM`: built in world space with `Math3D.DirectionAndUpMatrix(dir, hullTM[1], camWorld)`, then converted to player space with `Math3D.MatrixInvMultiply4(playerTM, camWorld, camLocal)`, plus `m_fUseHeading = 0` so the operator's head heading does not drag the view, and `StdFovUpdate` (`P:\scripts\4_world\entities\manbase\dayzplayer\dayzplayercamera_base.c:337`) for the field of view (zoom is `m_fFovMultiplier`). A working example is the turret camera of the third-party KT Roadkill Armed mod (`KT_TurretCamera.c`). The pawn is never released, so there is nothing to restore: the input controller stays enabled, there is no focus lock, and no input exclude is needed, which also removes the whole failure class of 37b. Verified in game on 2026-08-19 (LFHeli FLIR) after the `SelectSpectator` route cost four build cycles. Blocking the get out while the sight is up is then one condition, `modded class ActionGetOutTransport { override bool ActionCondition(...) }` (`P:\scripts\4_world\classes\useractionscomponent\actions\interact\actiongetouttransport.c:70`), not an input exclude.
38. **Three ways to read an input, all valid** (all three seen in LBmaster's production mods):
    - Simple: `g_Game.GetInput().LocalPress("UAMyAction", false)`, a one-line check.
    - Direct: `GetUApi().GetInputByName("UAMyAction").LocalPress()`, per frame.
    - Persistent: `UAIDWrapper wrapper = input.GetPersistentWrapper()` then `wrapper.InputP().LocalPress()`, the most robust for a stored reference.
39. **Avoid keybind conflicts.** Check VPP Admin Tools (`kP` copy position, `kEnd` toggle, `kHome` menu), Community Online Tools (`kHome`) and LBGroups; choose uncommon keys such as `kU` or `kO`.

## Rules from the knowledge pack's lessons list

Each keeps its `LL-NNN` label because the other files cite it.

- **LL-101**: the presence of a `proto native` symbol proves its signature, not that it works. For capture, rendering, hardware or I/O APIs, look for prior art and run a probe that produces the real result before you base a design on them.
- **LL-141**: before you vary the format of an engine API call, reproduce the exact vanilla call site. If that also fails, stop adjusting syntax and isolate the execution context: server or client, headless or with a GUI, the build, and the defines.
- **LL-016**: on the server, validate `sender`, its identity, and that its ID equals the target `PlayerBase`'s; also rate limit per player. Reject by default even when the payload holds nothing sensitive.
- **LL-186**: do not initialize opaque engine handles with literals (`FileHandle handle = 0`). Declare them uninitialized, assign the API's return value, and guard on the value that API documents.
