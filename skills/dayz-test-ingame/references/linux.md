# What changes on Linux

The other files in this folder describe the Windows workflow. This one lists what changes when the host is Linux. The Proton setup, the measured tool matrix and the pitfalls are in `skills/_shared/linux-proton.md`; the native server and the headless client have their own files here (`linux-native-server.md`, `linux-headless-client.md`).

Terms used below: "this box" and "this install" in dated findings mean the Windows test machine the measurement was taken on, not yours. `[EXACT]` marks a flag, path or behaviour that was verified in a real run; `[DESIGN]` marks something plausible that was not verified, so check it in game before relying on it. Tags such as `SP-078`, `LL-196` and `CLAIM-...` are the finding numbers of the knowledge pack this material came from; they are kept so that cross-references between files stay searchable. `DAYZ_INFRA.md` is that pack's infrastructure note (in this repo `skills/_shared/knowledge/environment-and-infra.md`); a tag like `[EXACT - DAYZ_INFRA.md §Section]` names the section of it that records the fact.

All of it is measured behaviour of the Linux server, Proton and the third-party dayz-mcp tool. It is not yet checked on `P:\`.

Everything in the other reference files is the Windows workflow and stays valid there. The points below say what changes for this skill.

- Linux host support in dayz-mcp was merged into `main` on 2026-11-14 in https://github.com/willy92wins/dayz-mcp/pull/411 (successor to closed PR #353); the managed-cycle observations here were measured on the `linux-port` branch on 2026-11-06 before #411 merged and were not re-measured on `main`. They do not verify managed binarization with assets. `dayz-test.ps1` and the approved-launcher registry are Windows-only. `dayz_test_run` runs on Linux (`mode=all`, `server` and `client`, with `build=true` and `dayz_test_close`/`dayz_test_stop`; measured 2026-11-06 on `linux-port`, `skills/_shared/knowledge/linux-proton-findings.md`, section 9). The policy's `diag_executable` picks the engine: `<game>/DayZDiag_x64.exe` runs both roles under Proton in headless sway sessions, as on Windows; `DayZServer` is a server-only project in rootless podman, and a client launch on it is refused with `client_needs_diag_executable`. Without dayz-mcp, the distributed helper is `skills/_shared/scripts/dayz-proton.sh headless start <state> DayZDiag <args>` (both diag roles under Proton; the server role uses `-server`). The native `DayZServer` with the retail client under Proton is the other route: `linux-native-server.md` (server tree, ports, reading the result) and `linux-headless-client.md` (headless client, the self-reporting AutoTest mod in `assets/autotest-mod/`, `dayz-client-test.sh`).
- `DayZDiag_x64.exe` runs under Proton: `dayz-proton.sh headless start <state> DayZDiag <args>`. Measured 2026-11-03 (1.30.164289): the client reaches the main menu, and `-server` with `-config=`/`-mission=`/`-profiles=` pointing into a Linux server tree loads the mission and runs the Central Economy. **A diag client only joins a diag server:** on the native `DayZServer` it stops at the modal `0x00020017, Client is using Diag exe while the server is not`, which only a screenshot shows. The diag pair joined and reached the world (measured 2026-11-06). `-filePatching` from an unpacked `-mod=` folder under Proton was **not verified**.
- `DayZDiag_x64.exe` under Proton loads a mod from an absolute `-mod=Z:\<linux path>\@Mod` and writes its logs into `-profiles=Z:\<linux path>` (measured 2026-11-05, 1.30.164289.70).
- Rules for the native-server route that fail silently or misleadingly when missed (details in `linux-native-server.md`): **removing CF from a tree whose storage was written with CF is an observed breakage** (it floods the log with `Scripted variables corrupted`); **adding CF needs a wipe is a hypothesis that was not isolated** (`Unknown type 'CF_Trace'` / `Can't compile "Engine" script module` is a compile error, not a storage read error, and the trees were rebuilt at the same time) - isolate first (rebuild with the same storage kept, or copy it aside) and rotate storage by rename with processes stopped to a destination that does not exist, never delete except in a disposable test tree you built; **run one server at a time on hosts with limited RAM** (about 7.5 GB RSS each with the Expansion bundle, measured on Linux; not an engine rule); **list servers with `ps aux | grep "[D]ayZServer"` and kill by PID**, because the process renames itself to `enfMain` and `pkill`/`pgrep -x DayZServer` silently match nothing; **compare each script module the mod contributes files to against a vanilla boot** (an unchanged count in such a module is the signal, e.g. a PBO outside `addons/`; the counter is an indicator only and a rise can come from other mods), and when an override silently does nothing, **put a deliberate syntax error in one of the mod's scripts**: a clean boot proves the file is not compiled. Compile errors are tagged `SCRIPT    (E)` (space-padded; grep `SCRIPT.*(E)`).
- Start the native `DayZServer` **without `-filePatching`** (with it the 1.30 server never finishes loading the landscape, measured 2026-11-04) and with a **relative `-mission=mpmissions/<name>`** (an absolute path leaves it without `init.c`'s `main`, so no player can connect, measured 2026-11-06; `skills/_shared/linux-proton.md`, section 5). Name `-mod=` and `-servermod=` **relative to the server tree** too (the reverse of "MOD PATHS MUST BE ABSOLUTE" in `windows-launch-cycle.md`; `linux-native-server.md`, section 3). Script iteration on the native server therefore means repacking the PBO, not loose files.
- A diag server and a diag client ran from one prefix with each role in its own headless Wayland sway (`PROTON_ENABLE_WAYLAND=1`, dayz-mcp, measured 2026-11-06). With `dayz-proton.sh headless`, a Wine prefix serves one display at a time, so use two `DAYZ_PROTON_HOME`s or one shared display (pitfalls in `skills/_shared/linux-proton.md`, section 5).
- Client and server must report the same game version (`dayz-proton.sh doctor`), or the join fails with `0x00020013`.
- `%LOCALAPPDATA%\DayZ` is `<prefix>/pfx/drive_c/users/steamuser/AppData/Local/DayZ`; pass `-profiles=<linux dir>` to keep logs where you read them. Linux host support in dayz-mcp was merged into `main` on 2026-11-14 in https://github.com/willy92wins/dayz-mcp/pull/411 (successor to closed PR #353; these observations were measured on `linux-port` before #411 merged and were not re-measured on `main`): the counterpart of the Steam-session check (`HKCU\Software\Valve\Steam\ActiveProcess`) is `~/.steam/steam.pid`, read-only - dayz-mcp never repairs or restarts Steam on Linux, and a logged-out Steam passes the check and fails at the client's Steam initialisation. `steam_session_stale` with a live `steam.pid` means an older `linux-port` build at or before `3a82bdc`, which still read `SteamPID` from `registry.vdf`: update to `main` (#411 or later) and restart the daemon; restarting Steam does not reliably help.
- `dayz_test_close` on Linux (measured 2026-11-06 on `linux-port`, before #411 merged): the order is right and the player logs out (`logout_finished: true`), and the server ends with `--- Termination successfully completed ---`. With a player **in the world** the client then exits with code 3 during teardown, after `Destroying game` and before its termination line, so the result is `graceful: false`, `exit_metrics_valid: false` (2 of 2 runs; the cause is unknown). Do not read client exit metrics from a Linux run; server metrics in the server's RPT are complete. A client still on its loading screen closed cleanly, with `graceful: true`. `dayz_test_stop` is a forced kill, as on Windows. `build=true` runs dayzmake from `PATH` (the Linux port merged in https://github.com/willy92wins/dayz-mcp/pull/411 accepts only the pinned v1.0.0 release binary; the 2026-11-06 runs on `linux-port` used the fork under its old name armake2) (`pack` with `pack_only`, otherwise `build --proton-binarize`) and writes `@Mod/Addons/<Mod>.pbo`; the full managed binarizing path was **not verified**, only the pack-only one. Not ported: `dayz_test_foreground` (a headless game has nothing to bring forward).
- Managed games have no input devices, so `use_state` reads `idle`, never `human`. As on Windows another session gets `run_protected` with `retry_after_s` until the 600 s abandon timer ends.
