# Formats and materials the viewer reads

What the viewer tool in `scripts/tools/dayz-3d-viewer` supports in `.paa`, `.p3d` and `.rvmat` files, how it turns a material into a Three.js one, and the faults that were found and fixed while building it. The vanilla checks were made on `P:\`; the rest is tool behaviour, measured by running the tool.

## PAA support

| Type | Code | Compression | Status |
|---|---|---|---|
| DXT1 | `0xFF01` | raw or LZO | supported, tested with real files |
| DXT5 | `0xFF05` | raw or LZO | supported |
| DXT3 | `0xFF03` | raw or LZO | supported |
| RGBA 4:4:4:4 | `0x4444` | LZSS | supported |
| RGBA 5:5:5:1 | `0x1555` | LZSS | supported |
| Luminance and alpha | `0x8080` | LZSS | supported |
| RGBA 8:8:8:8 | `0x8888` | LZSS | supported |
| Index palette | `0x4747` | LZSS or RLE | not supported (very rare); the tool stops with a message |

## Inside a PAA

- The file starts with a 2 byte type code, then optional tags (`OFFS`, `AVGC`, `MAXC`, `FLAG`, `SWIZ`). Checked on vanilla files: `P:\DZ\characters\vests\data\ballisticvest_co.paa` starts with the bytes `01 FF` (DXT1) and `P:\DZ\characters\vests\data\ballisticvest_nohq.paa` with `05 FF` (DXT5). Each tag is stored as `GGAT` plus its name backwards (`CGVA`, `CXAM`, `SFFO`), and the normal map also has `ZIWS`.
- Mipmaps are stored largest first, each with a 2 byte width, a 2 byte height and a 3 byte data size. The list ends with 6 zero bytes.
- DXT data goes to Pillow's DDS decoder behind a made-up DDS header.
- The top bit of the width field means the mipmap is LZO compressed and has to be unpacked before the DDS decode. Arma 2 and later files do this for large mipmaps. Measured on the vanilla `ballisticvest_co.paa` above: 10 mipmaps from 2048x2048 down to 4x4, the four from 2048 to 256 LZO compressed and the six from 128 down stored raw.
- The other formats use Bohemia's LZSS variant (ring buffer of 4096, filled with `0x20`).
- The `SWIZ` tag is read and stored but not applied, so a decoded `_nohq` PNG keeps the stored channel order. Do not treat it as the normal map the engine sees.

## P3D support

| Format | Support | Notes |
|---|---|---|
| MLOD (not binarized) | full | Read with the py3d fork. A model saved by Object Builder or generated by a script is MLOD. |
| ODOL (binarized) | not read | Vanilla game models are ODOL: `P:\DZ\characters\vests\plate_carrier_m.p3d` starts with the bytes `ODOL`. Convert with an external ODOL to MLOD converter first, then run the normal pipeline. Agentic-Z ships none. |

`cfgconvert -txt` does not work for ODOL input: CfgConvert converts `config.bin` and `config.cpp`, not `.p3d`.

Other limits of the converter, all still present (`scripts/tools/dayz-3d-viewer/KNOWN-ISSUES.md`):

- Proxy triangles are exported as visible geometry. Strip them first when the view has to match the in-game mesh.
- A LOD with resolution 1100 (the pilot view LOD) is classified as `shadow`, so it is never picked as the mesh to show.
- Only the best visual LOD is shown. There is no LOD switcher.
- There is no PNG to PAA encoder.

## RVMAT to a Three.js material

The parser reads the color keys and the stages, and the viewer maps them to a `MeshStandardMaterial`:

| RVMAT | Three.js | Rule |
|---|---|---|
| `diffuse[]` | base color | Used when the face has no texture. |
| `forcedDiffuse[]` | base color | Replaces `diffuse[]` when it is not zero. LED materials tint this way. |
| `specular[]` | metalness | Average of the three channels times 2, capped at 1. |
| `specularPower` | roughness | `1 - specularPower / 100`, not below 0.1. |
| `emmisive[]` | emissive color and intensity | Values above 1, such as `{0,40,0}`, are scaled down to 0 to 1. |
| Stage textures | none yet | The stages are parsed, but only the `_co` color texture is applied in the viewer. |

The key really is spelled `emmisive[]`: `P:\DZ\characters\vests\data\ballisticvest.rvmat:4`. Vanilla values above 1 exist, for example `emmisive[]={8,8,8,4}` at `P:\DZ\gear\tools\data\broom_birch_emissive.rvmat:4`.

The parser names each stage texture by its file suffix, not by its stage number. In a vanilla Super material the normal map is `Stage1` and the specular map is `Stage5` (`P:\DZ\characters\vests\data\ballisticvest.rvmat:57`); the stage roles are in `_shared/textures/rvmat-stages.md`. One effect of naming by suffix, seen when running `parse-rvmat` on that file: the environment map of `Stage7`, `dz\data\data\env_land_co.paa`, is listed under `textures.diffuse` because its name ends in `_co`. The viewer takes the color texture from the model's faces, so the picture is not affected.

## Materials for flat colored models

For a model that is one flat color per part, with no real texture detail, write one `.rvmat` per material with `diffuse[]` set to the base color (taken from the `.mtl` of the source model) and `texture=""`. No UVs are needed and no gaps can appear.

Do not bake such a model into a UV atlas. Baking many flat materials gives tiny islands over a black background, and any small UV drift samples the background: black holes, circles and smudges. Atlas baking is for models with real texture detail. This is modelling practice, not a fact about the game, so it is not checked on `P:\`.

## Faults found and fixed

1. **Backslash paths on Linux.** A P3D stores texture paths with Windows backslashes, such as `my_button\data\textures\base_co.paa`. `os.path.basename()` on Linux does not split them. Replace `\` with `/` before taking the base name.
2. **GLTFLoader inside a sandboxed frame.** A chat artifact frame blocks `fetch()` and `Request.clone()`. Loading a GLB with `loader.load()` or `loader.parse()` fails there, because the loader fetches buffer and image URIs itself. The embedded mode avoids GLTFLoader and builds the geometry from typed arrays.
3. **The other py3d.** `pip install py3d` installs a point cloud library from PyPI, not the P3D reader. Install the fork from `scripts/tools/py3d` and check `py3d.IS_DAYZ_FORK`.
4. **LZO on DXT mipmaps.** A PAA from Arma 2 or later compresses its large mipmaps (256 and up) with LZO, marked by the top bit of the width field. Decoding needs `python-lzo`, or `lzokay` plus the shim that `install-lzo-shim` writes.
