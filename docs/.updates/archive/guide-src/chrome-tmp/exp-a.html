Agentic-Z Agent Team

Agentic-Z 2.0.0, the DayZ modding plugin with a full mod team: 30 agents and 44 skills, graded by independent reviewers. Built on develop and not yet released to main. Same shape as the Dev Agent Team: you approve, a planner splits the work, leads hand it to workers, gatekeepers check it, and you give the final yes before you publish it.

The flowchart

You Planning Team leads Workers (one per task) Gatekeepers Playbook and knowledge packs

The leads run the mod review and layout check on each task. The orchestrator runs the build check, the in-game test and, when the plan lists behavior checks, the behavior test once per wave, one at a time, because there is only one mod folder and one test session. Workers run at the same time only when their tasks touch different files.

The AI features

Everything Agentic-Z 2.0.0 gives an AI agent, beyond the agents themselves: what each one is, and what it does for you.

FeatureWhat it isWhat it does for you
Knowledge and search
RAG search: game filesA searchable index of the vanilla DayZ files on your P drive (scripts, configs, layouts, materials, economy XML), built with Voyage AI code embeddings and stored in LanceDB.Agents find vanilla code by meaning, like "how does food spoil", instead of guessing class names. Tool: search_dayz_source.
File lookupOpens an exact file and line range on the P drive, and refuses anything outside it.Agents read the real source behind a search hit. Tool: get_dayz_file.
Cite then verifyA rule every agent follows: a search hit is a hint until the real file confirms it.Answers come with path:line references you can check, and fewer made-up classes.
Cited answers/dayz-ask answers a vanilla question, checks every hit against P:, and falls back to a keyword search when there is no index or key.A plain English question gets an answer with checked path:line citations.
Prebuilt index/dayz-search-download pulls a ready-made index from GitHub.A fresh install gets search without spending Voyage credits on embedding.
Knowledge packsDayZ know-how under .claude/skills/_shared/: ten specialist packs, an Enforce Script pack with references, patterns, framework guides and 13 worked examples, and the Figma rules.Agents load only the pack their task needs, so they work from facts checked against P:.
The agent team
Orchestrator and leadsA planner that runs as your main session, an architect, and one lead per team.You describe a mod once and approve a plan; the team splits and tracks the work.
SpecialistsDayZ experts for script, config, models, textures, UI, maps, server and Workbench, plus saving data, AI, vehicles, weapons, wearables, animation, audio and FX, and physics.Each task goes to an agent that knows that corner of DayZ.
GatekeepersMod review, layout check, build check, in-game test and behavior test, each answering PASS or FAIL.Nothing reaches you until it builds, loads in game with clean logs and, when the plan lists behavior checks, passes the behavior test.
Router/dayz-route keyword rules, then Jev when a TypeSafe key is set, then the Haiku dayz-router.Most requests reach the right handler with no model tokens.
Figma pipeline (optional)Three agents that turn a Figma frame into a checked DayZ .layout.An extra for people who design menus in Figma. Unused otherwise.
Agent creatorAn agent that writes and checks new agent files.New agents follow the same template and rules.
Rules and learning
Three tiersRepo rules, then DayZ rules (a core file plus five topic files), then agents and packs. The more specific tier wins.Every agent works from the same rules without each file repeating them.
Corrections become rules/dayz-record-correction drafts a rule from your correction and saves it after your yes.You correct a mistake once and the whole team stops making it.
Agent memoryEach worker agent keeps notes in the project's own .claude/agent-memory/ folder. Gates and the lead have none.Agents remember your project's choices between sessions, wherever you cloned it.
Hooks
Edit checkA syntax check after every config.cpp or .layout edit.A missing ; or } is fixed in the same turn, before a build fails on it.
Scope guardDenies edits to other mods while /dayz-scope-mod is set.An agent working on one mod can't damage another.
Paste-in routerReads what you paste: crash logs go to triage, types.xml chunks to a checked merge, Figma and GitHub links to their workflow.You paste, and the right workflow starts without explaining what it is.
Safety
Permission listsA shipped allow list and deny list for shell commands, and an explicit tool list on every agent.Agents can run the repo's own skills, but not inline code or new installs.
Read-only checkersThe mod reviewer, layout validator, build checker, in-game tester and debugger can't edit files, and the lead and physics specialist have no write tools.The agents that judge the work don't quietly change it.
Works everywhere
Three AI tools/sync-skills links the same skills into Claude Code, Codex and Gemini.Use whichever AI tool you like; the skills are the same.
Plugin or cloneInstall as a Claude Code plugin, or clone the repo as a mod template.Plugin users update through the marketplace; clones use /agentic-z-update.
Side panelagentic-z-panel 0.3.0, a second plugin with DayZ state and one-click buttons.Build, check, launch, stop, open the editors and read the logs without spending tokens.
Self-checking repo2,845 tests, 18 panel tests, answer tests for 23 of the 30 agents, a CI workflow on GitHub, and /docs-sync to keep the wiki matching the source.Broken agents, missing files and wrong tool names are caught before release.

How the grading works

The grades are not set by the author. Every agent, skill and shared file is graded by separate AI reviewers against Anthropic's published best practices for Claude Code. The reviewers are Claude instances started fresh for the job: they see the files, the rubric and the standards, never the earlier grades or the author's opinion. This is not an official Anthropic rating. It is a repeatable review that anyone can run again with the prompts below.

The final count

The final grades cover 164 items on origin/develop. 164 of them are at A+: 30 of the 30 agents, 44 of the 44 skills and 90 of the 90 shared items (hooks, the search server, the panel, scripts and wrappers, answer tests, rules files, knowledge packs and this method note). The final review graded every item at commit bcccc99; fresh graders then regraded items on develop after each fix round, and each item shows its latest grade, the newest given in rounds 7 to 9, after fix PRs #142 to #144. The grades come from final_grades.json and final_grades_shared.json; clean-repo was graded twice and counts once.

Who grades

  • Independent reviewers. Each round starts new Claude reviewers with no memory of earlier rounds. For the final review there were six: two for the agents, three for the skills, and one for everything shared (the hooks, the search server, the panel, the scripts and wrappers, the answer tests, the rules files, the knowledge packs and this note; a few shared files were not graded, as "Files not graded" under "Open items and decisions" lists).
  • Read only. Reviewers cannot edit files. They read every file, run the tests where the session allows it, and check claims against the code and the vanilla DayZ files on the P: drive. Three skill reviewers (for dayz-launch-objectbuilder, dayz-launch-workbench and dayz-search-download) could not run pytest because it was denied in their session, and said so in their reasons.
  • Separate fixers. Different agents fix what the reviewers found, each owning its own files. A fixer never grades its own work.
  • Regrade. New reviewers grade again after every fix round. An item only counts as A+ when an independent reviewer gives it A+.

What they grade against

  • Anthropic's standards: the Claude Code subagent documentation (code.claude.com/docs/en/sub-agents), the Agent Skills best practices (docs.claude.com/en/docs/agents-and-tools/agent-skills/best-practices), the Claude Code hooks reference (code.claude.com/docs/en/hooks) and plugins reference (code.claude.com/docs/en/plugins-reference), and for the search server, the Model Context Protocol tool guidance.
  • Agentic-Z's own rules: CLAUDE.md (Tier 1), the DayZ rules file and its topic files (Tier 2), the agent standard in agent-creator.md, and docs/prompt-conventions.md.
  • The real game: DayZ facts are checked against the vanilla files on P: (for example which file holds CfgSurfaces, which texture suffixes exist, which widget classes can be a layout's root). Six Enforce Script worked examples (01, 04, 05, 06, 08 and 09) are still marked as vendored and not checked on P:.

Specialist workflows

Every task goes through the same team loop: the user approves the plan, the orchestrator hands tasks to the leads, the leads hand them to specialists, and the gates check the work. Inside that loop each specialist works through its own steps. The specialists that write DayZ content look up vanilla first: they Grep for a class or symbol name they know, use RAG search for questions by meaning or after two or three failed greps, and read the real file before relying on a hit. The build engineer, docs writer, build checker, in-game tester and Figma cleaner have no RAG tool; they work from the mod, its logs or the Figma file.

  3. Adds RPCs only where client and server must talk, and checks which side runs each line.
  4. /dayz-lint and the build gate check and pack it (nothing compiles Enforce Script there); the in-game gate catches compile errors and reads script.log.
dayz-workbench-specialist
  1. Reads how vanilla Workbench plugins are registered.
  2. Writes the plugin script and its tool panel.
  3. Never opens Workbench itself: it tells the user to open it with /dayz-launch-workbench --mod <ModName>.
  4. Returns the plugin and the steps to load and run it.
dayz-persistence-specialist
  1. Lists every value that must survive a restart.
  2. Writes OnStoreSave and OnStoreLoad, with a version number written first.
  3. Adds an upgrade path so saves from the last version still load.
  4. Runs the data audit: every field is written and read back in the same order.
  5. Hands the audit to the server lead before release.
dayz-ai-specialist
  1. Studies how vanilla infected and animals decide what to do.
  2. Writes the behavior as its own script classes, never copied from another mod.
  3. Gives the server lead the spawn setup.
  4. In-game test watches the behavior and server performance.
Config lead
dayz-config-specialist
  1. Finds the closest vanilla parent class (Grep for known names, RAG search for questions by meaning) and reads its definition on disk, cited as path:line.
  2. Writes CfgPatches with the right requiredAddons, then the class itself.
  3. Matches hiddenSelections to the names in the model.
  4. /dayz-lint and the build gate check it loads.
dayz-vehicle-specialist
  1. Picks the closest vanilla vehicle as the parent.
  2. Writes the vehicle class and its simulation: engine, gearbox, axles, wheels.
  3. Adds attachment slots for doors, hood, trunk, wheels, battery and plug, and the fluids.
  4. Writes the CarScript or BoatScript class for seats, doors and damage.
  5. Gives the server lead a types.xml entry; the behavior gate spawns it and a person-run checklist covers driving.
dayz-weapon-specialist
  1. Picks the closest vanilla weapon as the parent.
  2. Writes the weapon, magazine and ammo classes and the attachment slots.
  3. Sets recoil and fire modes.
  4. Lists the model selections and memory points the art lead must provide.
  5. The behavior gate spawns it and fits each attachment; a person-run checklist covers firing and reloading.
Art lead
dayz-object-builder

  2. Names the selections and memory points the config and animations need, and writes model.cfg.
  3. Runs /dayz-p3d-audit after the user saves the model.

dayz-asset-specialist

  2. Packs them with /dayz-pack-texture.
  3. Writes the .rvmat for each material.
  4. Writes a look checklist for the user to check in Object Builder or in game; it never launches either.
dayz-wearables-specialist
  1. Picks the inventory slot and the closest vanilla item as the parent.
  2. Sets slots held, protection and insulation.
  3. Sets hidden selections so one model carries every color.
  4. Notes the proxy positions for the Object Builder specialist.
  5. The behavior gate wears each color class; a person checks in game how each color looks.
dayz-animation-specialist
  1. Lists the moving parts and their bones.
  2. Writes skeletonBones for the moving parts and the class Animations block in model.cfg; the Object Builder specialist keeps the rest of model.cfg.
  3. Gives the user the bone and selection names for their own Blender export.
  4. Names the script hook that plays the animation; the script specialist writes that code, and the in-game test uses it.

  3. Adds the script line that plays it.

  1. Reads the model's geometry LODs and mass.

Checks and fixes
dayz-mod-reviewer
  1. Reads the finished task against the DayZ rules file.
  2. Lists each problem with the specialist who owns it.
  3. Never edits files.
dayz-layout-validator
  1. Checks the .layout against the Figma-to-DayZ rules: file format and widget classes.
  2. Reports PASS or FAIL with each problem and its line. Never edits.
dayz-build-checker
  1. Runs only when /dayz-gate build itself breaks.
  2. Reads the AddonBuilder output and names the failing file.
dayz-ingame-tester
  1. Runs only when /dayz-gate ingame itself breaks.
  2. Reads the logs from the test session and reports what failed.
dayz-mod-debugger
  1. Gets new errors that triage does not know.
  2. Reads script.log, RPT and crash files back to the line that failed.
  3. Reports the cause, evidence, location and fix to whoever called it (the orchestrator or a lead), naming the worker agent that owns the fix.

How one task moves through the team

  1. You approve the mod plan from the architect, such as "a tactical vest with three retextures".
  2. The orchestrator splits it into tasks, like "write the vest's config.cpp entry".
  3. The right lead takes the task and starts a worker.
  4. The worker runs a RAG search, checks the real file, loads the playbook, and does the one task.
  5. The lead checks it with the mod reviewer (and the layout check for UI). When the whole wave is done, the orchestrator builds the mod and loads it in game. If anything fails, the debugger reads the logs and the task goes back with notes.
  6. Passing work is packed into a PBO and loaded on a test server.
  7. You give the final yes and publish it to the Steam Workshop with DayZ Tools Publisher.
