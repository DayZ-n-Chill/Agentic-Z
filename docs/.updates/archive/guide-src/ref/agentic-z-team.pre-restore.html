Agentic-Z Agent Team

Agentic-Z 2.0.0 is a Claude Code plugin and repo template for DayZ modding: 30 agents in .claude/agents/, 44 skills in .claude/skills/, shared knowledge packs, three hooks and the dayz-rag MCP search server, each graded by independent reviewers. Version 2.0.0 is on develop; main carries 1.6.0. The pipeline has the same structure as the Dev Agent Team: the user approves a plan, dayz-orchestrator splits it into tasks, dayz-lead hands each task to a worker, gates return PASS or FAIL, and the user gives final approval before publishing.

Architecture

You Planning Team leads Workers (one per task) Gatekeepers Playbook and knowledge packs

Gate order: dayz-lead runs dayz-mod-reviewer on every task and dayz-layout-validator on every .layout change. Once per wave, dayz-orchestrator runs the build gate, the in-game gate and, when the plan lists behavior checks, the behavior gate, one at a time, because there is one mod folder and one test session. Workers run in parallel only when their tasks touch different files.

Components

What Agentic-Z 2.0.0 adds to a Claude Code session, one row per component. Agents, skills, rule tiers and knowledge packs have their own sections below.

Knowledge and search
RAG search: game filessearch_dayz_source in the dayz-rag MCP server: an index of the vanilla DayZ files on P: (scripts, configs, layouts, materials, economy XML), embedded with Voyage AI code embeddings and stored in LanceDB. Agents find vanilla code by meaning ("how does food spoil") instead of guessing class names.
File lookupget_dayz_file returns an exact file and line range on P: and refuses any path outside it, so agents read the real source behind a search hit.
Cite then verifyRule in every agent: a search hit is a hint until the real file confirms it. Answers carry checkable path:line references and fewer invented classes.
Cited answers/dayz-ask answers a plain English question about vanilla, checks every hit against P:, and falls back to keyword search when there is no index or key.
Prebuilt index/dayz-search-download pulls a prebuilt index from GitHub, so a fresh install gets search without spending Voyage credits on embedding.

Agent team

Gatesdayz-mod-reviewer, dayz-layout-validator, and the /dayz-gate build, in-game and behavior gates, each returning PASS or FAIL. Work reaches the user only after it builds, loads in game with clean logs and, when the plan lists behavior checks, passes the behavior gate.
Router/dayz-route keyword rules, then TypeSafe's Jev when TYPESAFE_API_KEY is set, then the Haiku dayz-router agent. Most requests reach the right handler with no model tokens.

Rule tiersRepo rules, DayZ rules, then agents and packs; the more specific tier wins, and no file repeats another. See "Rule tiers".
Corrections become rules/dayz-record-correction drafts a rule from a user correction and saves it after the user approves, so a mistake corrected once is corrected for the whole team.
Agent memory19 of the 30 agents set memory: project and keep notes on the project's decisions in its own .claude/agent-memory/ folder, wherever it is cloned. The gates, dayz-lead and dayz-router have none.
Hooks (hooks/hooks.json; each exits silently on its own errors, so a hook bug never blocks the session)
Edit checkhooks/edit_check.py, a PostToolUse hook on Edit, Write and MultiEdit: syntax check of config.cpp and .layout files. A problem returns {"decision": "block"} with each file:line, so a missing ; or } is fixed in the same turn, before a build fails on it.

Permission lists.claude/settings.json ships 26 allow rules and 11 deny rules, and every agent has an explicit tools list. Agents can run the repo's own skills, but not inline code (python -c, node -e) or new installs (npm install, npx).

Grading method

Every agent, skill and shared file is graded by AI reviewers, not by the author, against Anthropic's published best practices for Claude Code. Each reviewer is a Claude instance started fresh for the job: it sees the files, the rubric and the standards, never the earlier grades or the author's opinion. This is not an official Anthropic rating; it is a repeatable review that anyone can rerun with the prompts under "Reproducing the review".

Current counts

The grades cover 164 items on origin/develop. 164 of them are at A+: 30 of the 30 agents, 44 of the 44 skills and 90 of the 90 shared items (hooks, the search server, the panel, scripts and wrappers, answer tests, rules files, knowledge packs and this method note). Each item shows its latest grade. The grades come from final_grades.json and final_grades_shared.json; clean-repo is graded in two batches and counts once.

Reviewers

  • Independent reviewers. Every review starts new Claude reviewers with no memory of earlier reviews. A full review uses six: two for the agents, three for the skills, and one for everything shared (the hooks, the search server, the panel, the scripts and wrappers, the answer tests, the rules files, the knowledge packs and this note). The few shared files that are not graded are listed under "Limits".
  • Read only. Reviewers cannot edit files. They read every file, run the tests where the session allows it, and check claims against the code and the vanilla DayZ files on the P: drive. A reviewer whose session does not allow pytest says so in its reasons.
  • Separate fixers. Other agents fix the findings, each owning its own files. A fixer never grades its own work.
  • Regrade. New reviewers grade every fixed item again. An item counts as A+ only when an independent reviewer gives it A+.

Standards

  • Anthropic's standards: the Claude Code subagent documentation (code.claude.com/docs/en/sub-agents), the Agent Skills best practices (docs.claude.com/en/docs/agents-and-tools/agent-skills/best-practices), the Claude Code hooks reference (code.claude.com/docs/en/hooks) and plugins reference (code.claude.com/docs/en/plugins-reference), and for the search server, the Model Context Protocol tool guidance.
  • Agentic-Z's own rules: CLAUDE.md (Tier 1), the DayZ rules file and its topic files (Tier 2), the agent standard in agent-creator.md, and docs/prompt-conventions.md.
  • The real game: DayZ facts are checked against the vanilla files on P: (for example which file holds CfgSurfaces, which texture suffixes exist, which widget classes can be a layout's root). Six Enforce Script worked examples (01, 04, 05, 06, 08 and 09) are marked as vendored and not checked on P:.

GradeMeaning

in .claude/agents/agent-creator.md: precise third-person description with an

CLAUDE.md, .claude/skills/_shared/dayz-conventions.md and the team flow; a Report

anything lower, name a concrete defect a user would actually hit.

Limits

  • Live DayZ session. Nothing in 2.0.0 has run against a real DayZ session: not the team loop, the in-game, behavior or visual gates, or the panel's launch buttons. The behavior and visual gates are tested with fixtures only.
  • Published version. Version 2.0.0 is on develop; main carries 1.6.0.
  • Answer tests. 23 of the 30 agents have them. dayz-build-checker, dayz-ingame-tester, dayz-mod-architect, dayz-lead, dayz-orchestrator, dayz-router and figma-to-dayz-layout have no question file.
  • Files not graded. Nine answer test files, expansion_style.md, examples/layouts.md and the nine enscript-style/ section files.
  • Unchecked examples. Six of the 13 Enforce Script worked examples are marked as vendored and not checked on P:.
  • Preflight exceptions. The DayZ rules file has 14 exception entries naming 21 skills that skip the preflight gate; docs/dayz-modding.md lists five of them.

Domain specialists

Eight specialist agents, each with its own knowledge pack, work under the team leads alongside the workers, and /dayz-lint runs inside the build gate. Every fact in the packs is checked against the vanilla files on P: and written fresh; nothing is copied from other mods.

Knowledge verification cycle

Each specialist and its pack go through the same cycle: research, a reference written in Agentic-Z's own words, a check of every fact against P: by a separate agent, answer tests, wiring into the lead, router and reviewer, and independent grading.

The specialists have not run in a live DayZ session; see "Limits".

Skills

44 skills in .claude/skills/, each a slash command any agent or user can run. 40 ship in the plugin; /sync-skills, /agentic-z-update, /docs-sync and /clean-repo are for clones only. Preflight gating of the 40 plugin DayZ skills:

  • 18 run /dayz-preflight first (preflight itself is the check).
  • The DayZ rules file has 14 exception entries naming 21 skills, each with its reason. Some of them read P:: /dayz-lint, /dayz-balance, /dayz-conflict-check, /dayz-recipe, /dayz-layout-preview and /dayz-upgrade-guard only read files and write a report, and /dayz-ask only checks that P: is mounted. /dayz-gate gates through the scripts it calls, and /dayz-stop-test skips the check so it still works as an emergency stop.
  • /dayz-particles is a reference skill with no script.

Knowledge packs

All under .claude/skills/_shared/. Any worker can load any pack for a task.

  • Citations. Most game facts cite a P: file and line, and the reviewers opened the cited lines.
  • Integrity test. Checks less: each Markdown pack file that is not exempt must name a vanilla P: file at least once. It does not check the .c and .layout worked examples.
  • Unchecked. Six of the 13 worked examples (01, 04, 05, 06, 08 and 09) are marked as vendored and not checked on P:.
  • Frameworks. The Community Framework and Dabs guides are checked against those frameworks' own scripts.
  • Exempt from the citation rule. The style guides, folder indexes and a few notes.

Specialist workflows

Per-agent steps inside the "Task lifecycle". Agents that write DayZ content look up vanilla first: Grep for a known class or symbol name, RAG search for questions by meaning or after two or three failed greps, then read the real file before relying on a hit. dayz-build-engineer, dayz-docs-writer, dayz-build-checker, dayz-ingame-tester and figma-node-normalizer have no RAG tool; they work from the mod, its logs or the Figma file.

AgentSteps
Script lead
dayz-script-specialist
  1. Searches the vanilla scripts for the class it will change and reads the real file.
  2. Writes a modded class in the right layer (3_Game, 4_World or 5_Mission) and calls super.
  3. Adds RPCs only where client and server must talk, and checks which side runs each line.
  4. /dayz-lint and the build gate check and pack it (neither compiles Enforce Script); the in-game gate catches compile errors in script.log.
dayz-workbench-specialist
  1. Reads how vanilla Workbench plugins are registered.
  2. Writes the plugin script and its tool panel.
  3. Never opens Workbench itself: it tells the user to open it with /dayz-launch-workbench --mod <ModName>.
  4. Returns the plugin and the steps to load and run it.
dayz-persistence-specialist
  1. Lists every value that must survive a restart.
  2. Writes OnStoreSave and OnStoreLoad, with a version number written first.
  3. Adds an upgrade path so saves from the last version still load.
  4. Runs the data audit: every field is written and read back in the same order.
  5. Hands the audit to the server lead before release.
dayz-ai-specialist
  1. Studies how vanilla infected and animals decide what to do.
  2. Writes the behavior as its own script classes, never copied from another mod.
  3. Gives the server lead the spawn setup.
  4. In-game test watches the behavior and server performance.
Config lead
dayz-config-specialist
  1. Finds the closest vanilla parent class and reads its definition on disk, cited as path:line.
  2. Writes CfgPatches with the right requiredAddons, then the class itself.
  3. Matches hiddenSelections to the names in the model.
  4. /dayz-lint and the build gate check it loads.
dayz-vehicle-specialist
  1. Picks the closest vanilla vehicle as the parent.
  2. Writes the vehicle class and its simulation: engine, gearbox, axles, wheels.
  3. Adds attachment slots for doors, hood, trunk, wheels, battery and plug, and the fluids.
  4. Writes the CarScript or BoatScript class for seats, doors and damage.
  5. Gives the server lead a types.xml entry; the behavior gate spawns it and a person-run checklist covers driving.
dayz-weapon-specialist
  1. Picks the closest vanilla weapon as the parent.
  2. Writes the weapon, magazine and ammo classes and the attachment slots.
  3. Sets recoil and fire modes.
  4. Lists the model selections and memory points the art lead must provide.
  5. The behavior gate spawns it and fits each attachment; a person-run checklist covers firing and reloading.
Art lead
dayz-object-builder
  1. Specifies the LODs (visual, geometry, fire geometry, view geometry, memory) as numbered Object Builder steps for the user, since it cannot edit a .p3d.
  2. Names the selections and memory points the config and animations need, and writes model.cfg.
  3. Runs /dayz-p3d-audit after the user saves the model.
  4. Hands the selection names to the config lead.
dayz-asset-specialist
  1. Checks each texture has the right suffix (_co, _nohq, _smdi and the rest).
  2. Packs them with /dayz-pack-texture.
  3. Writes the .rvmat for each material.
  4. Writes a look checklist for the user to check in Object Builder or in game; it never launches either.
dayz-wearables-specialist
  1. Picks the inventory slot and the closest vanilla item as the parent.
  2. Sets slots held, protection and insulation.
  3. Sets hidden selections so one model carries every color.
  4. Notes the proxy positions for the Object Builder specialist.
  5. The behavior gate wears each color class; a person checks in game how each color looks.
dayz-animation-specialist
  1. Lists the moving parts and their bones.
  2. Writes skeletonBones for the moving parts and the class Animations block in model.cfg; the Object Builder specialist keeps the rest of model.cfg.
  3. Gives the user the bone and selection names for their own Blender export.
  4. Names the script hook that plays the animation; the script specialist writes that code, and the in-game test uses it.
UI lead
dayz-ui-specialist
  1. Reads the vanilla layout closest to the new screen.
  2. Writes the .layout and the script class that drives it.
  3. Builds icons into an imageset with /dayz-build-imageset.
  4. The layout checker checks it against the Figma-to-DayZ rules and /dayz-layout-preview draws it; the in-game test opens it.
figma-node-normalizer
  1. Reads the Figma frame.
  2. Cleans layer names and structure so they map to DayZ widgets.
  3. Hands the clean tree to the layout converter.
figma-to-dayz-layout
  1. Turns the clean tree into a DayZ .layout.
  2. Uses only widget types the game supports.
  3. Hands it to the layout checker.
Server lead
dayz-server-admin
  1. Writes types.xml entries with /dayz-edit-types.
  2. Adds events, spawn points and gameplay settings where needed.
  3. Splits large economy files with /dayz-split-types.
  4. Sets up a missing test server instance with /dayz-add-server (which starts nothing) and returns the /dayz-launch-test command instead of starting the server.
dayz-map-specialist
  1. Writes layers.cfg and the surface and clutter configs; if the user's own layers.cfg is needed and missing, it stops and asks.
  2. Gives numbered steps for the DayZ Editor export and the Terrain Builder import and generation, which the user carries out.
  3. Returns the files and the steps to rebuild the map.
Release lead
dayz-build-engineer
  1. Packs the mod with /dayz-build-pbo.
  2. Starts the test session with /dayz-launch-test.
  3. Reports the build result to the release lead, who passes it to the orchestrator.
dayz-docs-writer
  1. Reads what changed in the wave.
  2. Updates the README, changelog and classname list.
  3. With /dayz-release-pack, writes the Workshop text and server-owner notes.
Any lead
dayz-audio-fx-specialist
  1. Reads the vanilla sound or particle closest to the request.
  2. Writes the sound shader and sound set, or the particle with /dayz-particles.
  3. Adds the script line that plays it.
  4. In-game test listens and looks.
dayz-physics-specialist
  1. Reads the model's geometry LODs and mass.
  2. Finds the fault: missing geometry, wrong mass or bad collision.
  3. Hands the fix to the Object Builder or config specialist; it never edits.
  4. A person-run in-game test drops, throws and shoots it, which the behavior gate cannot.
Checks and fixes
dayz-mod-reviewer
  1. Reads the finished task against the DayZ rules file.
  2. Lists each problem with the specialist who owns it.
dayz-layout-validator
  1. Checks the .layout against the Figma-to-DayZ rules: file format and widget classes.
  2. Reports PASS or FAIL with each problem and its line.
dayz-build-checker
  1. Runs only when /dayz-gate build itself breaks.
  2. Reads the AddonBuilder output and names the failing file.
dayz-ingame-tester
  1. Runs only when /dayz-gate ingame itself breaks.
  2. Reads the logs from the test session and reports what failed.
dayz-mod-debugger
  1. Gets new errors that triage does not know.
  2. Reads script.log, RPT and crash files back to the line that failed.
  3. Reports cause, evidence, location and fix to its caller (the orchestrator or a lead), naming the worker that owns the fix.

Task lifecycle

  1. The user approves the mod plan from dayz-mod-architect, for example "a tactical vest with three retextures".
  2. dayz-orchestrator splits it into tasks, for example "write the vest's config.cpp entry".
  3. dayz-lead for the matching team takes the task and starts a worker.
  4. The worker runs a RAG search, checks the real file, loads the playbook, and does the one task.
  5. The lead gates it with dayz-mod-reviewer (plus dayz-layout-validator for UI); after the wave the orchestrator builds the mod and loads it in game. Known errors go to their owner through triage, new ones to dayz-mod-debugger, and the task returns with notes.
  6. Passing work is packed into a PBO and loaded on a test server.
  7. The user approves and publishes to the Steam Workshop with DayZ Tools Publisher.
